# 问渠系统设计：把 80% 的精力花在读路径上

> 一个技术内容分享平台，从「多级缓存 + 检索增强生成」出发的工程取舍。

内容社区有个很有意思的流量特征：**读写极度不对称**。一篇文章写出来只有作者点开几次，但一篇爆款可能被几万人同时读。这意味着系统的复杂度不该平均分配——写路径可以慢、可以重、可以异步，读路径必须快，而且要能在缓存全部失效的瞬间不被打穿。

问渠就是按这个思路设计的。下面把几个关键决策拆开讲。

## 一、整体结构

```
           ┌─────────────┐
   浏览器 ──│  Nginx/静态  │── React 前端（Vite 构建）
           └──────┬──────┘
                  │ /api
           ┌──────▼──────────────────────────────┐
           │  Spring Boot 3 / Java 21             │
           │  ├─ auth      双令牌 + Redis 白名单    │
           │  ├─ knowpost  发布流水线 + Feed 读路径  │
           │  ├─ counter   位图判重 + SDS 计数       │
           │  ├─ relation  Outbox + Canal 事件      │
           │  ├─ search    IK 分词 + 复合打分        │
           │  └─ llm       RAG 索引 + SSE 流式问答   │
           └──┬────┬────┬────┬────┬────┬──────────┘
              │    │    │    │    │    │
           MySQL Redis  ES  Kafka Canal  OSS
```

一句话概括分工：**MySQL 是唯一事实来源，Redis 扛读，ES 扛搜，Kafka + Canal 负责把变更异步扩散到各处，OSS 存所有大块内容。**

## 二、读路径：缓存怎么分层

Feed 是访问最集中的入口，缓存形态分两层，Redis 内部再按 key 的粒度拆成三类：

| 层级 | 存什么 | 失效粒度 |
| --- | --- | --- |
| L1 本地 Caffeine | 整页响应（公共 Feed / 我的发布 / 详情） | 单机，靠 TTL 逐出 |
| L2 Redis 片段缓存 | 分页 ids 列表、单条 item、计数 | 按文章 ID，可按小时分片 |

为什么页面加了缓存还要片段缓存？因为**失效粒度不同**。一篇文章被编辑，理论上只需要让包含它的那些页失效，但页面 key 是按「页码 + 尺寸」组织的，你不知道某篇文章出现在第几页。片段缓存解决的就是这个问题：页面缓存未命中后重新组装时，绝大多数片段还能命中，只有真正变化的那几条需要回源数据库。

三个保护机制叠在上面：

**热点探测**。按 60 秒滑动窗口统计单篇文章的访问次数，分三档（50 / 200 / 500 次），命中越高档 TTL 延长越多（+20s / +60s / +120s）。逻辑很朴素：既然大家在看它，它短时间内大概率不会变。

**随机抖动**。片段缓存的 TTL 会额外叠加 0~30 秒的随机偏移，避免一批 key 在同一秒集体过期——这是缓存雪崩最经典的触发方式。

**单飞锁（single-flight）**。同一页并发回源时，只放一个请求去查库，其余在锁内等待并优先重查缓存。这挡住的是缓存击穿：一个热门 key 刚过期，一万个请求同时打进来。

## 三、写路径：为什么发布要拆成五步

发布一篇带图的文章，客户端要做五件事：

```
1. POST /drafts              → 建草稿，拿到 postId
2. POST /storage/presign     → 每张图拿一个预签名 PUT URL
3. PUT 到 OSS                → 图片直传，不经后端
4. 正文 .md 直传 + 回执       → 带 ETag 和 SHA-256
5. PATCH 元数据 → POST 发布   → 校验通过后状态置为 published
```

核心是第 3、4 步：**文件不经过 Java 服务**。后端只签发一个有有效期、绑定对象键和 Content-Type 的预签名 URL，浏览器直接 PUT 到 OSS。这样做的收益很直接——一张 5MB 的图不会占用应用服务器的内存和线程，也不会把带宽压在网关上限上。

正文回执带 SHA-256，是为了防止「文件传了但内容坏了」。服务端不重新下载校验（那等于又传一遍），而是信任客户端算出的哈希，与前端上传后回读的值比对。对 Markdown 这种几 KB 到几百 KB 的文本，这个成本可以接受。

数据库里只存指针：

```sql
content_url          -- OSS 访问地址
content_object_key   -- 对象键
content_etag         -- ETag
content_size         -- 字节数
content_sha256       -- 内容哈希
```

**正文一个字都不进 MySQL**。原因有三个：TEXT/BLOB 大字段会撑大行、把 InnoDB 的页填充率打下来；全量备份体积翻几十倍；CDN 完全无法参与加速。

## 四、计数：为什么不用 `UPDATE ... SET like = like + 1`

点赞是最容易被低估的场景。单个用户的点赞是低频操作，但爆款文章的点赞是「每秒几百次写同一行」。

所以这里的写路径是异步的：

```
用户点赞 → 位图判重（O(1)）→ 投递 Kafka → 消费端聚合 → 定时刷写 SDS
```

**位图判重**：每个用户 ID 对应一个 bit，`bitmap[userId / 32768][userId % 32768]` 分片存储。判断「这个人点过没」就是一次 GETBIT，天然幂等，不需要额外去重表。

**SDS 紧凑计数**：Redis 的 SDS 结构里按固定段长存多个指标，一个内容的点赞/收藏/评论数挤在几十个字节里。相比每个指标一个 String key，内存差一个数量级。

**异步聚合**：Kafka 消费端把增量先累加到 Redis Hash（`agg:{schema}:{etype}:{eid}`），每秒批量折叠进 SDS。写放大被摊平成固定的 O(1) 次 Redis 调用。

**灾备回放**：这是我觉得最值得说的一点——如果 Redis 整个丢了，可以从 Kafka 的 earliest 位点重放全部点赞事件，直接从位图重建计数。代价是回放耗时，但**数据不会永久丢失**，因为事实源头在 Kafka 里。

## 五、关系链：Outbox 模式解决什么问题

关注关系要同时维护四份数据：关注表、粉丝表、用户维度的关注数、列表缓存。

如果代码里写成「插关注表 → 发消息更新计数」两步，中间进程挂了就会不一致。经典解法是 **Transactional Outbox**：

```java
@Transactional
void follow(long from, long to) {
    relationMapper.insertFollowing(from, to);   // 业务表
    outboxMapper.insert(event);                  // 同一事务写发件箱
}
```

两张表在同一个本地事务里提交，要么都成功要么都回滚。然后 Canal 订阅 MySQL binlog，把 outbox 表的新增行投递到 Kafka，下游消费者再去更新计数和缓存。

好处是**业务代码里没有一行「发消息」的代码**——它不关心 MQ 是否可用、是否重复投递。代价是链路上多了一个 Canal 组件，且事件是最终一致的（毫秒到秒级延迟）。对这个场景完全可以接受：关注数晚 200 毫秒更新，没人在意。

消费端做了幂等：Redis 里去重键带 10 分钟 TTL，同一个事件重复消费不会重复计数。

## 六、搜索：召回、打分、分页

索引字段直接用 IK 分词器声明，标题的索引和检索用不同粒度：

```yaml
title:  analyzer: ik_max_word, searchAnalyzer: ik_smart
body:   analyzer: ik_max_word
tags:   keyword        # 只过滤，不参与召回
title_suggest: completion
```

`ik_max_word` 建索引时切得细（"中华人民共和国" → 中华/华人/人民/共和国/中华人民共和国），`ik_smart` 检索时切得粗。前者保证召回，后者保证精度。

查询用 `function_score` 包一层 `bool`：

```java
function_score(
  query: bool(
    must:   multi_match(q, fields: "title^3", "body"),  // 标题权重 ×3
    filter: status = "published",
    filter: tags ∈ [选中标签]                            // 可选
  ),
  functions: [
    fieldValueFactor(like_count, log1p) × 2.0,
    fieldValueFactor(view_count, log1p) × 1.0
  ],
  boostMode: Sum
)
```

三个细节值得展开：

- **`title^3`**：标题命中比正文命中更说明相关，这是最省事的调权手段。
- **`log1p`**：点赞 10000 和 20000，线性加权会差一倍，但它们的「热度差」并没有那么大。取对数把差距压到合理区间。
- **`boostMode: Sum`**：相关性和热度**相加**而非相乘，避免零赞的新文章被乘成 0 分。新内容需要曝光机会，这是产品层面的考量。

分页用 `search_after` 而不是 `from/size`：

```java
sort: [score desc, publish_time desc, like_count desc, view_count desc, content_id desc]
```

`from=10000` 时 ES 要在每个分片上取出前 10010 条再丢弃，越翻越慢；`search_after` 带上一次最后一条的排序值，直接从那个位置往后取。代价是**排序键必须唯一且稳定**，所以最后要用 `content_id` 兜底，否则相同排序值的文档会在翻页时重复或丢失。

联想建议走另一条路——completion suggester：

```java
suggest: completion(prefix: "分布", field: "title_suggest")
```

它底层是 FST（有限状态转换器），把前缀树压进内存，前缀匹配不需要跑查询计划，能做到亚毫秒。这也是为什么它只适合**前缀补全**，不适合模糊纠错。

## 七、RAG：让问答有据可依

详情页右侧有一个 AI 伴读面板，能针对当前这篇文章提问。链路是：

```
切分正文 → 向量化（text-embedding-v4, 1536 维）→ 写入 ES 向量索引
提问 → 检索 topK=5 切片 → 拼 Prompt → 大模型流式生成 → SSE 推给前端
```

几个工程上的取舍：

**幂等删除保单一版本**。文章每次编辑，先按 `postId` 删掉旧切片再重建，而不是增量追加。否则同一篇文章会有多个版本的切片混在索引里，检索时自相矛盾。

**预索引降低首问等待**。发布时就建立索引，而不是等第一次提问时才现建。用户点开面板提问时，索引已经就绪，省掉几秒的建索引时间。

**内容变更才重建**。索引元数据里存了正文的 `contentSha256` 和 `contentEtag`，重建前先比对，内容没变直接跳过。

**流式而非一次性返回**。用 `Flux<String>` + `text/event-stream`，前端用 `fetch + ReadableStream` 手写解析（而不是 EventSource，因为需要 `AbortController` 随时中止）。用户能看到字一个个出来，感知延迟从「等 8 秒」变成「0.3 秒开始有反应」。

## 八、踩过的坑

写下来给同样在搭这套东西的人：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| ES 建索引失败 | 服务端没装 IK 插件，mapping 里的 `ik_max_word` 解析不了 | 插件版本必须和 ES 主版本严格一致 |
| 客户端连不上 ES | `elasticsearch-java` 与 ES 服务端跨大版本 | 两者保持同一大版本 |
| Kafka 启动即退出 | Windows 11 移除了 `wmic`，官方启动脚本依赖它 | 直接用 `java -cp libs/* kafka.Kafka` 起 |
| Kafka 报 `AccessDeniedException *.checkpoint.deleted` | 上次被强制结束，留下只读的清理标记 | 删掉 `__cluster_metadata-0` 下的 `*.checkpoint.deleted` |
| Canal 报 `errno = 1236` | 位点缓存指向已被清理的 binlog | 删 `meta.dat` 与 `h2.mv.db` 重新定位 |
| 搜索搜不到长文后半段 | `body` 字段截断 4000 字符 | 后续按段落切片索引，或正文分片检索 |

## 九、如果重做一次

几个还在待办清单上的事：

- **正文分片索引**。现在只索引前 4000 字，长文的后半段搜不到。正确做法是按段落切分，每片单独建索引，检索时聚合回文档。
- **浏览量埋点**。`view_count` 目前恒为 0，所以搜索打分里那一项加权实际没生效。补一个异步埋点（Redis 计数 + 定时落库）就能激活。
- **用户索引**。现在只能搜内容，搜不到人。加一个用户索引，支持按昵称和问渠号找人。
- **缓存一致性观测**。现在靠 TTL 兜底最终一致，缺一套「缓存与库差异」的监控指标。

## 小结

回看这套设计，真正花时间的不是 CRUD，而是三件事：

1. **让读路径扛住**——三级缓存 + 热点延长 + 抖动 + 单飞，四个机制各挡一种失效模式；
2. **让写路径解耦**——预签名直传绕开应用服务器，Outbox + Canal 绕开双写不一致；
3. **让搜索说得清**——召回靠分词粒度，排序靠权重设计，分页靠游标，每一处都有明确的取舍理由。

内容社区的技术难点从来不是「把文章存下来」，而是「一篇文章被十万人同时打开的那一分钟」。这套架构就是为那一分钟准备的。
